# 04. 技術アーキテクチャ

## 1. スタック

| 層 | 選択 | 理由 |
|---|---|---|
| 言語 | TypeScript（strict） | シム部の型安全性。数値コードでも enum/単位の取り違えを防ぐ |
| ビルド | Vite | 起動と HMR が速い。反復速度がこの種のチューニング作業では最重要 |
| 描画 | Canvas2D（`ImageData` 直書き）→ **WebGPU** | Phase 1 は Canvas2D で十分。Phase 2 で場ごと GPU に載せる（§8） |
| UI | 素の DOM + 軽量な状態管理（自作 signal で足りる） | React は不要。UI は数十要素しかない |
| 並行 | Web Worker（シム専用）→ **WebGPU compute** | メインスレッドの描画を止めない。GPU 戦略は §8 |
| テスト | Vitest | シムの検証テスト（§05）が本命 |
| 依存 | 最小限 | シミュレーションの中身は全部自前。ライブラリを挟むとチューニングできない |

**採用しないもの**: React、ゲームエンジン（Phaser 等）、物理エンジン、ECS フレームワーク。本作はグリッド上の数値計算とデータ可視化であり、それらは全部邪魔になる。

## 2. スレッド構成

```
┌──────────────── Main Thread ────────────────┐
│  UI (DOM)                                   │
│  Renderer (Canvas)                          │
│  InputController → 介入コマンドをキューへ     │
└───────────┬─────────────────────▲───────────┘
            │ postMessage         │ SharedArrayBuffer（読み取り）
            │ (Command[])         │ + postMessage（イベント/統計）
┌───────────▼─────────────────────┴───────────┐
│            Sim Worker                        │
│  SimLoop → Subsystem[] を stepYears 順に駆動  │
└─────────────────────────────────────────────┘
```

### 2.1 データ受け渡し

- **フィールド（大きい）**: `SharedArrayBuffer` に置き、メインスレッドは読み取り専用で参照。ダブルバッファ + `Atomics` によるフレーム番号で tearing を防ぐ。
  - SAB が使えない環境（COOP/COEP ヘッダなし）へのフォールバック: transferable な `ArrayBuffer` を毎フレーム ping-pong する。設計上どちらでも動くように、`FieldStore` インターフェースで抽象化する。
- **介入コマンド（小さい）**: メインスレッド → Worker へ `postMessage`。
- **イベント / 統計（小さい）**: Worker → メインへ `postMessage`。系統樹、寄与分解、タイムラインマーカーはここを通る。

## 3. データレイアウト

### 3.1 SoA + Float32Array

```ts
class FieldStore {
  readonly W: number
  readonly H: number
  readonly cellCount: number
  private buffer: SharedArrayBuffer
  readonly elevation:   Float32Array
  readonly temperature: Float32Array
  // ...
  /** クレード別バイオマス。[clade * cellCount + cell] */
  readonly biomass: Float32Array
  idx(x: number, y: number): number { return y * this.W + ((x % this.W) + this.W) % this.W }
}
```

- **AoS（`Cell[]`）は使わない。** 256×128 = 32,768 セル × 20 フィールド × 数十ティック/秒 では、オブジェクト配列は GC とキャッシュミスで死ぬ。
- 全フィールドを 1 本の `SharedArrayBuffer` にオフセット配置する。セーブは**バッファ丸ごとのシリアライズ**で済む。

### 3.2 セル面積テーブル

`areaByRow: Float64Array(H)` を初期化時に一度だけ計算。全球平均・総量の計算は**必ずこれで重み付けする**（§01-2.1）。

### 3.3 隣接アクセス

東西ループのため、`idx()` に剰余が入る。ホットループ（ラプラシアン等）では剰余を毎回計算せず、**行の左右端だけ特別扱いして中央は素の添字**で回す。

```ts
// 中央: x = 1 .. W-2 は分岐なし
// 端:   x = 0 と x = W-1 だけループ処理
```

## 5. 寄与台帳（Ledger）— 最重要の横断規約

§03-5.3 の寄与分解パネルは、**後から実装できない**。全サブシステムが最初から従う規約にする。

```ts
type CauseTag =
  // 放射
  | 'solar' | 'greenhouse.co2' | 'greenhouse.ch4' | 'greenhouse.h2o'
  | 'greenhouse.pressureBroadening'        // 🔴 N2 分圧
  | 'antigreenhouse.haze'                  // ★ 符号が逆
  | 'albedo.ice' | 'albedo.vegetation' | 'albedo.land'
  | 'albedo.cloud' | 'albedo.ccn'          // ★ 生物起源の雲凝結核
  | 'aerosol.volcanic' | 'aerosol.anthropogenic'
  | 'transport'
  // 炭素
  | 'volcanism.arc' | 'volcanism.hotspot' | 'volcanism.lip'
  | 'weathering.kinetic'                   // ★ レジームを区別する
  | 'weathering.supplyLimited'             //    どちらで律速されたかが読めること
  | 'weathering.seafloor'
  | 'photosynthesis' | 'respiration' | 'burial'
  | 'subduction.carbonate' | 'degassing.mantle'
  // 栄養と海洋
  | 'phosphorus.weathering' | 'phosphorus.burial'
  | 'phosphorus.anoxicRelease'             // ★ 正のフィードバック
  | 'ocean.stratification' | 'ocean.anoxia' | 'ocean.euxinia'
  | 'ocean.acidification'
  // 生命
  | 'evolution.speciation' | 'evolution.extinction'
  | 'evolution.capabilityGain' | 'evolution.endosymbiosis'
  | 'predation' | 'competition'
  // 固体地球
  | 'tectonics.modeChange' | 'tectonics.orogeny' | 'tectonics.erosion'
  | 'water.mantleUptake' | 'water.degassing'
  // 文明
  | 'society.emission' | 'society.landUse' | 'society.nutrientFlux'
  | 'society.collapse'
  // 介入
  | 'intervention.*'

interface Ledger {
  /** target への delta を cause 由来として記録 */
  add(target: LedgerTarget, delta: number, cause: CauseTag): void
  /** ティック境界で確定し、リングバッファに落とす */
  commit(year: number): void
}
```

**書き方の規約:**

```ts
// ❌ 直接書き換える
globals.co2 -= weatheringFlux

// ✅ 台帳経由
ledger.add('co2', -weatheringFlux, 'weathering')
// commit() が globals.co2 に反映し、同時に履歴に残す
```

- 台帳はリングバッファに `N` ティック分（数千）保持。それより古いものは時代ごとに集約して圧縮。
- コスト: 1 ティックあたり数十エントリ程度。無視できる。
- **副次的な利益**: 保存則の検査（炭素の総量が保存されているか）がテストで自動化できる。数値バグの発見が劇的に楽になる。

## 6. 決定論性

| 規則 | 理由 |
|---|---|
| `Math.random()` 全面禁止（lint ルールで機械的に禁止） | リプレイと seed 共有の前提 |
| `Date.now()` をシムロジックで使わない | 同上 |
| サブシステムごとに独立した PRNG ストリームを持つ | あるサブシステムの乱数消費回数が変わっても他が壊れない |
| `Set` / `Map` の反復順序に依存しない | JS では挿入順で安定だが、事故りやすい。ソート済み配列を使う |
| 浮動小数の非決定性に注意 | 同一エンジン内なら決定的。クロスブラウザの完全一致は**保証しない**（リプレイは同一ブラウザ前提と明記） |

**リプレイフォーマット**: `{ version, seed, initialParams, commands: [{ year, type, payload }] }`。数 KB。共有可能。

## 7. パフォーマンス目標

| 項目 | 目標 |
|---|---|
| グリッド | Phase 1: 512 × 256 = 131,072 セル / Phase 2: 1024 × 512（§8.2） |
| クレード数 | 同時 60 まで |
| シムティック | 60 ticks/s 以上（Worker 上、地質エポック時） |
| 描画 | 60 fps（レイヤ再生成は必要時のみ） |
| メモリ | フィールド全体で < 20 MB |

### 想定ボトルネックと対策

1. **EBM のラプラシアン反復** — 平衡解へのガウス・ザイデル反復。ティックごとの反復数を適応的にする（変化が小さければ反復を減らす）。
2. **クレード × セルのバイオマス更新** — 60 × 32,768 = 200 万要素。**優占クレードのみ全セル更新**し、個体数が閾値未満のクレードは活動セルのバウンディングボックス内だけ回す（スパース化）。これが効かないと詰む。
3. **描画** — `ImageData` を 1 枚作って `putImageData` → `drawImage` で拡大。レイヤが変わっていないフレームは再生成しない。
   Phase 2 で場が GPU バッファに載れば、この転送自体が消える（§8.1）。

## 8. GPU 計算戦略 (WebGPU)

### 8.1 結論

**CPU 先行 → 物理が固まってから GPU 移植。ただし初日から移植可能な形で書く。**

| 段階 | 実装 | グリッド |
|---|---|---|
| Phase 1（物理の確立） | TypeScript + Worker + Float32Array | 256×128 → 512×256 |
| Phase 2（解像度と生命） | WebGPU compute へホットカーネルを移植 | 1024×512 |
| Phase 3（余裕があれば） | 全カーネル GPU、描画もゼロコピー | 2048×1024 |

**GPU を最初からやらない理由:**

1. **物理がまだ確定していない。** `proto/RESULTS.md` §5 の通り、較正で 5 つの微妙なバグを踏んだ。
   いずれも「モデルは正しく書けているのに結果が現実と合わない」類で、**WGSL で同じことをやるのは苦行**（printf もデバッガも無い）。
2. **反復速度が全て。** この種のチューニング作業では、1 回の試行が 10 秒か 60 秒かが最終的な品質を決める。
3. **移植は機械的にできる** — CPU 版を §8.5 の規則に従って書いておけば。

**GPU をやる理由（Phase 2 で必ず来る）:**

1. **生態系が唯一の本当のボトルネック**（§8.3）。クレード数 × セル数で、しかも完全に並列。
2. **場が GPU バッファに載れば描画がタダになる。** CPU→GPU の毎フレーム転送が消え、
   レイヤ表示は storage buffer を読むフラグメントシェーダになる。
3. 2026 年現在、**WebGPU は Chrome / Firefox / Safari / Edge すべてに標準搭載済み**
   （Firefox の Linux / Android は 2026 年内に対応予定）。もう実験的技術ではない。

### 8.2 解像度の議論 — 解像度は精度を買わない

| グリッド | セル数 | 赤道でのセル幅 | |
|---|---|---|---|
| 256×128 | 32,768 | 157 km | 開発用 |
| **512×256** | 131,072 | **78 km** | **CPU での実用上限・出荷既定** |
| 1024×512 | 524,288 | 39 km | GPU 移植で解禁 |
| 2048×1024 | 2,097,152 | 20 km | 過剰。生態系のコストが爆発する |

参考: 現代の GCM は概ね 25–100 km。**512×256 の時点で既に標準的な GCM と同等の解像度**にいる。

> **重要**: 本作の物理は EBM とパラメタライズされた降水であり、**解像度を上げても物理は正しくならない**。
> 律速はパラメタリゼーションの側にある。
> **解像度が買うのは視覚的・ゲーム的な可読性**（河川網、山脈、海岸線、大陸の形）であって、精度ではない。
> ここを混同すると、意味のない解像度競争に時間を溶かす。

### 8.3 カーネル別の適性

| カーネル | 計算量 (512×256) | GPU 適性 | 備考 |
|---|---|---|---|
| **生態系（個体数動態）** | 60 クレード × 131k = **7.9M** | ★★★ | **最大のボトルネックで、完全に並列。GPU 移植の第一目標** |
| EBM の緩和反復 | 131k × 40 反復 | ★★★ | 5 点ステンシル。GPU の得意技 |
| アルベド・OLR・降水 | 131k | ★★★ | 完全にローカル |
| 侵食（stream power） | 131k | ★★★ | ローカル |
| 地殻パーセルの移流 | 粒子数 | ★★☆ | 移流は並列、ラスタライズは scatter（atomics 必要） |
| **D8 流下・集水積算** | 131k | ★☆☆ | **依存グラフの走査。GPU が最も苦手** |
| 窪地埋め (depression filling) | 131k | ☆☆☆ | priority-flood は本質的に逐次 |
| グローバル・リダクション | 131k → 1 | ★★☆ | 決定論性に注意（§8.4） |
| 寄与台帳の集計 | 30 原因 × 131k | ★★☆ | 融合すれば安い。§8.4 の固定小数点で |

**D8 集水積算をどう扱うか** — これが唯一の設計上の難所:

- **選択肢 A（推奨）**: CPU に残す。**河川網は地質時間スケールでしか変わらない**ので、
  数百ティックに 1 回、Worker 上で更新すれば十分。GPU 側は結果を読むだけ。
- 選択肢 B: MFD（多方向流下）の反復緩和に置き換える。並列化しやすいが河川が滲む。
- 選択肢 C: 並列 flow accumulation アルゴリズムを実装する。**やらないこと。** 労力に見合わない。

### 8.4 決定論性 — WebGPU で最も注意が必要な点

`docs/04-6` の決定論性要件は、GPU では成立させ方が変わる。

#### (a) WebGPU の atomics は i32 / u32 のみ 🟢

**浮動小数の atomicAdd は WebGPU に存在しない。** これは制約であると同時に**救い**でもある。
float の atomicAdd は加算順序が実行ごとに変わり、**非結合性により結果が run-to-run で変わる**。

→ **リダクションは固定小数点の整数 atomics で行う。**

```wgsl
// 浮動小数を固定スケールで整数化してから atomicAdd する。
// 整数加算は結合的かつ厳密なので、順序が変わっても【ビット単位で同一】の結果になる。
const SCALE: f32 = 1048576.0;   // 2^20
atomicAdd(&accum, i32(value * SCALE));
```

スケールは量ごとに決める（温度、フラックス、バイオマスで桁が違う）。
オーバーフローに注意 — 131k セル × 最大値 × SCALE が i32 に収まること。収まらなければ
階層リダクション（ワークグループ内で f32 の決定的ツリー加算 → ワークグループ間で整数 atomics）にする。

**この方式は実務で使われている**（WebGPU の勾配バッファが float atomics 不在のため固定スケール整数を使うのと同じ）。

#### (a-2) ★実装後の訂正 — 固定小数点を使ってよい量とそうでない量がある 🟢

実装して測った結果、**固定小数点で足りるのは「大きさが既知で有界な量」だけ**だと分かった。

| 量 | 桁の変動 | 採用した方式 |
|---|---|---|
| 放射の集計（`meanS`, `meanSaIce`, `meanT`) | ほぼ一定（S≈340, T∈[−120,500]） | 固定小数点 atomics ✅ |
| CG の内積（`dot(r,z)`, `dot(p,Ap)`) | **反復とともに 4〜6 桁下がる** | f32 の二段リダクション ✅ |

CG の内積を 2^20 の固定スケールで積むと、`rz` が 1e-7 まで落ちた時点で有効数字が消え、
`beta` が壊れて CG が収束しなくなる。**固定小数点は動的レンジが狭いという弱点がある。**

→ CG のスカラーは **f32 のまま順序を固定して二段で畳む**。

```
一段目: ワークグループ内 64 要素の固定順ツリー加算 → part[wg] に書く
二段目: 1 スレッドが part[0..NG) を固定順で逐次加算
```

**順序が固定なら IEEE754 の加算は決定論的**なので、atomics を使わずに (a) と同じ保証が得られる。
むしろ atomics より強い — ワークグループの完了順に依存しないため。

副次的な利点として、CG ループから `clearAcc` ディスパッチが消えて 1 反復あたり 10 → 8 ディスパッチになった。

#### (a-3) ★実装で踏んだ罠 — ストレージバッファのバインド数は既定 8 本 🔴

**`maxStorageBuffersPerShaderStage` の保証値は 8**（WebGPU の下限保証。SwiftShader も実 GPU も同じ）。

場ごとに 1 本ずつバインドする素直な設計は 26 本になり、**`createBindGroupLayout` が失敗する**。
しかも WebGPU は**その場では例外を投げない** — 「エラー状態のオブジェクト」を返し、
使用時に静かに何もしない。結果として**全部ゼロが返るだけ**の状態になり、原因に辿り着くのに時間を要した。

**対処 2 つ:**

1. **場を 1 本のバッファに詰める。** `F[slot * n + i]` でアクセスする。
   オフセットは W,H が決まればコンパイル時定数なので、パイプライン生成時にソースへ埋め込む。
   結果、ストレージバッファは **4 本**（行定数 `R` / 場 `F` / アキュムレータ `acc` / スカラー `sc`）。
2. **`device.onuncapturederror` を必ず張り、solve の前に確認する。**
   張らないと黙って壊れる。これは WebGPU で最初にやるべきこと。

カーネル本体は物理そのままの見た目（`temp[i]`, `cgP[idx(x,y)]`) で書き、
ソース組み立て時に正規表現で `F[temp_ + (i)]` に置換している（`src/gpu/climateShaders.ts` の `packRefs`）。
可読性を落とさずに制約を満たすため。

#### (b) 超越関数はベンダ間でビット一致しない 🟢

`exp` / `log` / `pow` の実装精度は ULP レベルでベンダごとに違う。
本作の風化式は `exp((T−T0)/13.7)`、放射強制は `log(CO2/280)` を使うので、**そのままでは移植不能**。

**対処:**

1. **超越関数を使う計算は CPU 側のボックスモデルに閉じ込める。**
   グローバル・スカラー（CO₂、O₂、リザーバ、風化フラックス）は 50 個程度しかない。
   これらは Worker 上の TypeScript で計算し、結果を uniform buffer で GPU に渡す。
2. どうしてもセル単位で必要な場合（例: 局所的な適応度のガウス窓）は、
   **CPU と GPU で同一の多項式近似を共有する。** `core/mathfixed.ts` と WGSL に同じ係数を置き、
   ユニットテストで一致を検証する。

#### (c) 到達可能な決定論のレベル

| レベル | 達成可能性 |
|---|---|
| 同一デバイス・同一ブラウザで再現 | ✅ 上記 (a)(b) を守れば可能 |
| 同一 GPU ベンダ間で再現 | 🟡 概ね可能 |
| クロスベンダでビット一致 | ❌ **不可能**（fma の融合有無、ドライバ最適化） |

**したがってリプレイの位置づけを変える:**

- 共有するのは `{seed, initialParams, commands[]}` のまま（数 KB）
- ただし**軌跡のチェックサム**を一定間隔で記録し、再生時に照合する
- 乖離を検出したら「この再生は元の惑星と異なります」と**明示する**。黙って別の惑星を出さない
- **シナリオの合否判定をビット一致に依存させない**

### 8.4b ★実装結果 — 気候ソルバの GPU 移植（M4.5、実装済み）

`src/gpu/` に実装済み。CPU 版（`src/sim/climate.ts`）と同じ物理・同じ数値解法
（擬似時間発展 + 南北ライン前処理付き PCG）を WGSL で書き直したもの。

#### 設計上の中心的な判断: PCG のループ全体を GPU 上で回し切る

内積の結果を毎反復 CPU に戻すと、読み戻しの遅延（1 回 ≈ 0.5ms）が
100 反復で 50ms になり、**CPU 版より遅くなる**。
スカラー（alpha, beta, rz, pAp）も GPU バッファ `sc` に置き、**反復回数を固定**して、
**1 solve につき読み戻しを 1 回**にした。

代償として収束判定ができない。だがこれは元々許容できる —
不正確 Newton は緩い線形解を許すし、ゲームは毎ティック解き直すので
1 ティックで完全収束させる必要がない（気候は準静的）。

#### 検証結果（`npm run gpu-verify`）

CPU の厳密解（`cgTol 1e-3, maxOuter 300, tol 1e-6`）を基準とした最大セル差:

| 解像度 | 場面 | GPU 設定 | ディスパッチ | 最大差 |
|---|---|---|---|---|
| 128×64 | 冷スタート | N10×CG100 | 8110 | **0.0003 K** |
| 128×64 | 温スタート CO₂+2% | N4×CG40 | 1324 | **0.0055 K** |
| 256×128 | 冷スタート | N10×CG100 | 8110 | **0.0006 K** |
| 256×128 | 温スタート CO₂+2% | N3×CG30 | 753 | **0.12 K** |

CPU は f64、GPU は f32 なので厳密一致はしない。0.0006 K は f32 の丸めの範囲。

#### ★測って分かった、予想と違ったこと

**1. GPU 版は CPU 版の 1/10 の CG 反復で同じ精度に達する。**

256×128・CO₂ +2% の摂動で:

| | CG 反復数 | 最大差 |
|---|---|---|
| CPU 対話設定（`maxOuter 8`） | 924 | 0.10 K |
| GPU N3×CG30 | **90** | 0.12 K |

理由は GPU が速いからではなく、**擬似時間の刻み方が違う**から。
CPU は毎回 `cOcean/(10B)`（≈ 0.4 年）から始めて SER 則で登るので、
最初の数回の Newton 反復がほとんど進まない。
GPU は反復回数が固定なので**最初から大きな刻み（≈ 純 Newton）を使う**しかなく、
温スタート（前ティックの解のすぐ近く）ではそれが正解だった。

**2. しかしこの改善は CPU 版には移植できない。** ← 測って否定した仮説

「では CPU 版も大きな刻みから始めればよいのでは」と考えて `pseudoDt0` を追加して測ったところ、**逆効果**だった:

| CPU の `dt0`（256×128, CO₂+2%） | 時間 | CG 反復 | 最大差 |
|---|---|---|---|
| 既定 `cOcean/(10B)` | **495ms** | 724 | 0.113 K |
| 1e3 | 938ms | 1356 | 0.124 K |
| 1e9 | 1281ms | 2016 | 0.201 K |

刻みを大きくすると `w·c/dt` の項が消えて**対角が小さくなり、CG の条件数が悪化する**。
CPU は CG を許容誤差まで回す（`cgTol`）ので、その分だけ反復が増えて損をする。
GPU は CG を固定回数で打ち切る（不正確 Newton）ので、条件数の悪化が反復数に跳ね返らない。

→ **同じ「良い刻み」が、CG の停止条件によって得にも損にもなる。**
`pseudoDt0` はオプションとして残したが、CPU 版の既定は据え置き。

#### 速度について、正直な限界

**この環境（WSL）では実 GPU の速度を測れない。** `/dev/dxg` と `libd3d12` はあるが
`dzn` Vulkan ICD が無いため、Chromium は SwiftShader（CPU によるソフトウェア実装）に落ちる。
上の表の所要時間はすべて SwiftShader のもので、**実 GPU の性能とは無関係**。

測れたのは **正しさ**と**ディスパッチ回数**だけ。実 GPU での損益分岐は
ディスパッチ 1 回あたりのオーバーヘッド（概ね 2〜5μs）で決まる:

- 温スタート N3×CG30 = **753 ディスパッチ** → オーバーヘッドだけで 1.5〜3.8ms
- 256×128 の CPU 版は 12.6ms

→ **256×128 では拮抗、512×256 以上で GPU が有利**というのが理屈上の見立て。
セル数が 4 倍になっても GPU のディスパッチ回数は変わらない（1 ディスパッチあたりの
スレッド数が増えるだけ）のに対し、CPU は 4 倍の時間がかかるため。

**実測は Windows 側のブラウザで行う必要がある。** HUD の `solve` 欄に `GPU` と出ていれば
GPU バックエンドが選ばれている。

#### 構成

| ファイル | 役割 |
|---|---|
| `src/gpu/device.ts` | WebGPU 初期化、ソフトウェア実装の検出、検証エラーの収集 |
| `src/gpu/climateShaders.ts` | WGSL カーネル群とソース組み立て（`packRefs`） |
| `src/gpu/gpuClimate.ts` | バッファ確保、パイプライン生成、ディスパッチ列 |
| `src/gpu/verify.ts` | CPU との数値一致検証（ブラウザ内で実行） |
| `scripts/gpu-verify.ts` | 上を CDP でヘッドレス実行し合否を返す |

`World.climateBackend` に刺す。**無ければ黙って CPU 版に落ちる**ので、
WebGPU が無い環境でも動作は変わらない。CPU 版の同期 API はそのまま残してあり、
94 個のテストとスクリプト群は影響を受けない。

### 8.5 移植可能な CPU 実装のための規則 ★実務上これが一番重要

Phase 1 の TypeScript を以下の形で書けば、Phase 2 の WGSL 移植はほぼ機械的になる。
**逆に、これを守らずに書くと後で全面書き直しになる。**

| # | 規則 | 理由 |
|---|---|---|
| 1 | **SoA の Float32Array**（既に §3） | GPU の storage buffer にそのまま載る |
| 2 | **ping-pong バッファ。in-place 更新を禁止** | GPU カーネルは read buffer → write buffer。同一バッファの読み書きは競合 |
| 3 | **カーネルは純関数 `(読み取り場) → セル 1 個の出力`** | 1 スレッド = 1 セル に対応する |
| 4 | **scatter（他セルへの書き込み）を避ける** | GPU では atomics が必要になり、決定論性も壊れる。gather に書き換える |
| 5 | **`Array.prototype.reduce` を使わない。明示的な固定順序ツリー加算** | 加算順序を実装で固定する。§8.4(a) |
| 6 | **超越関数はボックスモデル（スカラー）側に閉じ込める** | §8.4(b) |
| 7 | **動的確保をティックループ内で行わない** | GPU にヒープは無い |
| 8 | **データ依存の分岐を避け、`step` / `mix` で書く** | ワープダイバージェンス |
| 9 | **東西ループは halo（袖領域）で処理する。ホットループ内で剰余を取らない** | 分岐と剰余は GPU でも CPU でも遅い |
| 10 | **カーネルの寸法を 8 の倍数に保つ** | ワークグループサイズ 8×8 に自然に割れる |

規則 4 の例（地殻パーセルのラスタライズ）:
```
❌ scatter: 各パーセルが自分の落ちるセルに書き込む → atomics 必要
✅ gather:  各セルが自分の近傍のパーセルを集める → 空間ハッシュを一度作れば並列
```

### 8.6 段階的移植の順序

Phase 2 で移植する順番。**一度に全部やらないこと。** 各段階で CPU 版と数値を照合する。

1. **描画** — 場を GPU バッファに置き、フラグメントシェーダで表示。**これだけで転送コストが消える**
2. **生態系** — 最大の利得（§8.3）
3. **EBM の緩和反復** — ステンシル。教科書的
4. **アルベド / OLR / 降水 / 侵食** — ローカルなので簡単
5. **地殻パーセル** — gather 化（規則 4）が必要
6. **D8 集水積算は移植しない** — CPU に残す（§8.3）

各段階で **CPU 版と GPU 版の出力を比較するテスト**を持つこと。
許容誤差は相対 1e-5 程度（超越関数の差があるため厳密一致は求めない）。

### 8.7 実行環境

- **WebGPU は Worker から使える。** メインスレッドは描画とUIに専念させる
- `SharedArrayBuffer` が不要になる（COOP/COEP ヘッダの制約から解放される）のは副次的な利点
- WebGPU 非対応環境（Firefox の Linux / Android など、2026 年時点）向けに
  **CPU パスを 512×256 で維持する**。`FieldStore` を介した抽象化（§2.1）がここで効く

## 8.8 解像度独立性 ★M5 以降で最も効く設計規則

**セルは離散化の都合であって、物理ではない。**
同じ seed なら、格子解像度が変わっても同じ惑星でなければならない。

### なぜ今これを書くか

フェーズ1 でこの種のバグを **3 回**踏んだ。

| バグ | 症状 |
|---|---|
| 島弧の成長を「セルあたりの厚さ増加率」で書いた | 弧の幅は有限差分の性質上つねに約 2 セルなので、絶対的な弧の面積が解像度に反比例する。64×32 で +26%、96×48 で ±0% と食い違った |
| 水蒸気の減衰を「セルあたりの割合」で書いた | 減衰長が解像度で変わり、大陸内陸の乾燥度がばらついた |
| 風化の較正が供給律速の割合を解像度依存にした | 定常 CO₂ がずれた |

**そして M5（生命）はこの罠が桁違いに多い。** 生命はセルの上に乗るから:

| 素朴に書くと | 何が起きるか |
|---|---|
| 分散を「セル/ティック」で書く | 解像度を上げると種の広がる速度が遅くなる |
| 種分化を「セルあたりの確率」で書く | 解像度を上げると進化が速くなる（セル数が増えるから） |
| 生息域を「セル数」で判定する | 解像度で絶滅しやすさが変わる |
| 個体数の閾値を「セルあたりの生物量」で書く | 解像度で存続条件が変わる |
| 競合を「隣接セル」で書く | 相互作用距離が解像度で変わる |

### 規則

**新しい量は必ず物理単位で書く。** セルはそこから導く。

| 量 | 正しい表現 | 導出 |
|---|---|---|
| 速度（分散・移流） | km/yr | `セル/ティック = 速度 × dt / セル幅` |
| 密度（生物量・地殻） | kg/m²、km³ | `セルの値 = 密度 × cellArea[y]` |
| 率（種分化・絶滅） | 1/(m²·yr) | `セルの確率 = 率 × cellArea[y] × dt` |
| 減衰・相互作用の距離 | km | `セルあたりの係数 = 1 − exp(−セル幅/距離)` |
| 総量（個体数・体積） | 面積積分 | `Σ 値 × cellArea[y]`（`grid.globalMean` と同じ固定順序） |

**セル幅は緯度で変わる**ことに注意（`2πR cos φ / W`）。
東西方向の距離を扱う量は、必ず緯度ごとのセル幅を使う（水循環の実装が例）。

### 守られているかの検査

`tests/resolution.test.ts` が不変条件として固定している。

- 生成直後の巨視量（陸地面積・気温・氷・アルベド・供給律速・降水・地殻体積）が **2% 以内**
- 較正（風化の 2 拘束）が解像度に依存しない
- 時間発展しても同じ惑星と呼べる範囲に留まる
- 同じ seed なら解像度が違っても同じ大陸配置になる（単位球上の 3D ノイズによる）

**M5 で生命を足すときは、このテストにクレード数・総バイオマス・主要な
ケイパビリティの獲得年代を追加すること。**

## 9. テスト戦略

シミュレーションゲームのテストは「正しい絵が出るか」ではなく **「系が期待した振る舞いをするか」**。

| 種別 | 内容 |
|---|---|
| **保存則テスト** | 炭素・水・エネルギーの総量が、フラックスの収支と一致するか（台帳から自動検証） |
| **平衡テスト** | 現在の地球パラメータを入れたら全球平均気温 ≈ 15℃、CO₂ ≈ 280ppm で安定するか |
| **分岐テスト** | 太陽定数を徐々に下げると、ある値でスノーボールに落ちるか（ヒステリシスも確認） |
| **フィードバックテスト** | CO₂ を 4 倍にして放置 → 風化により 10⁵〜10⁶ 年で元の水準に戻るか（＝ガイアが機能しているか） |
| **サーモスタット故障テスト** ★ | 侵食速度を 0 に固定 → 供給律速に落ち、CO₂ が単調増加するか（§01-4.2）。**負のフィードバックが無条件でないことの検証** |
| **反温室テスト** ★ | CH₄ を増やしていくと、ある比でヘイズが立ち上がり**温度が下がりに転じる**か（§01-3.3） |
| **様式遷移テスト** ★ | マントル初期温度を振ると、mobileLid に到達する惑星としない惑星が分かれるか（§01-6.1） |
| **はしご不在テスト** ★ | 多細胞性が複数のクレードで独立に獲得されるか。単一系統に固定されていないこと（§02-2.1） |
| **合流テスト** ★ | 内部共生が発生し、`parentIds.length > 1` のクレードが生じるか（§02-2.4） |
| **メデア・テスト** ★ | 光合成クレードの繁栄が `oxygenToxicity` の高いクレードを絶滅させるか。**生命が生命を殺す経路が生きているか**（§02-3.1） |
| **可逆性テスト** ★ | 気候悪化で `agriculture` 比率と `hierarchy` が**下がる**か。一方向に上がり続けないこと（§02-4.3, 4.4） |
| **崩壊の非全滅テスト** ★ | 崩壊後に population > 0 かつ knowledge が部分的に残るか（§02-4.5） |
| **決定論テスト** | 同一 seed + 同一コマンド列 → 同一の最終ハッシュ |
| **数値健全性テスト** | 全フィールドが NaN/Inf を含まない、クランプが発動していない |

**これらのテストは仕様書そのもの。** マイルストーンごとに §05 で対応するテストを定義する。
